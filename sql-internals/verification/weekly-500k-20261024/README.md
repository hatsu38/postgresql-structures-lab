# 各週を50万件にそろえたデータでの再測定

2026年10月24日に、読了日時の生成式を変えて測り直した。本100万冊、読書記録200万件、本の番号と本ごとの読了件数は変更していない。新しいSQLとログはこのフォルダに置き、過去の測定ファイルは変更していない。

## 日時の割り当て

`setup.sql`では、番号nから`((n - 1) * 104729) % 2000000`を計算する。104729と2000000は互いに素なので、0から1,999,999までが重複せずに現れる。その値に28日分の秒数2,419,200を掛けて2,000,000で割り、整数同士の除算で秒未満を切り捨ててから、2026年8月24日0時に足している。

50万件ごとに7日分になるため、各週がちょうど50万件になる。時刻は保存順に並ばず、200万件の日時はすべて異なる。日ごとの件数まで均等になるわけではなく、9月20日は71,428件だった。

`conditions.log`で、本100万冊、記録200万件、異なる日時200万件、各週50万件、記録がある本736,097冊を確認した。`check-results.log`では、本ごとの件数が旧式の本番号生成式とすべて一致することも確認している。

## 測定環境

- PostgreSQL 18.6（Debian 18.6-1.pgdg13+2）、Dockerの専用コンテナ。既存の実験DBは使用していない。
- イメージ：`postgres@sha256:86c951e05bf56c93d95d397747fb8820ac76cc3bedb78f43abd83eedbe3666ae`
- `shared_buffers=128MB`、`block_size=8192`、`hash_mem_multiplier=2`、`default_statistics_target=100`。
- 各接続で`max_parallel_workers_per_gather=0`、`jit=off`、通常は`work_mem=4MB`。ソートとLIMITの比較では64MB、外部ソートでは64kBに変更。
- バックグラウンドで状態が変わらないように、この測定コンテナは`autovacuum=off`で起動。第11章の複製テーブルには明示的にVACUUMを実行した。
- SQLは下表の順序で実行した。キャッシュを測定間で空にしていない。実行時間の倍率を一般化するための測定ではない。
- `ANALYZE`の標本は毎回変わるため、推定件数は再実行すると異なることがある。

第11章のSQLは、`ch11/vm-index-state-20261022`の観察SQLを再利用した。レコードの挿入順と大きさは変えていないため、観察対象の保存場所も元の`(4428,6)`と新しい`(10810,151)`のままだった。第11章の本文と図で説明している動きは変わらない。第1〜4章のbooks、第8〜9章の小さな一時テーブル、第10〜11章のcatsや二接続の実験は、今回変更した日時生成式を使わない。

本文で使っている図には今回変わる数値が含まれていないため、画像は変更していない。外した旧第12章の図と、過去のREADMEの記録にある499,998件は、以前の測定として残している。

## 再実行

DockerとPython 3がある環境で、このフォルダを指定して実行する。新しい専用コンテナで測定し、終了時に削除する。SQLと採取済みログは上書きせず、指定した新規ディレクトリに再測定ログを保存する。

```sh
python3 run.py /tmp/weekly-500k-local
```

作業ディレクトリはこのフォルダとする。空のDBに`setup.sql`を1回だけ実行し、その後は表の順序でSQLを実行する。`ch11.sql`の`heap_state`が調べる保存場所は今回の配置なので、変更したデータで再利用するときは最初のctidと照らし合わせる。

`run.py`でも別の空のコンテナから全工程を再実行し、結果の一致を確認した（`rerun-check-results.log`）。`check-manuscript.py`は、原稿のフォルダを引数で指定すれば実験用リポジトリ側からも実行できる。

```sh
python3 check-manuscript.py /path/to/zenn/books/postgresql-explain-algorithms
```
